# TV3 isolated read performance

This dependency-free Python harness implements the independent read-performance
portion of TV3-11. Expiry jobs, durable notifications, gateway reconciliation,
Redis failure behavior and production capacity remain separate work.

## Safety and measured routes

`read_load.py` accepts only a loopback HTTP(S) origin. Its first HTTP request is
`GET /api/commerce/runtime`; the response must explicitly identify `tv3-commerce`
and set `isolatedData: true`. Each worker has distinct customer/staff cookie jars
and repeats that guard before logging in through the existing session endpoint
using `/api/csrf`. Passwords and usernames come from environment variables only.
Authentication, cookies, CSRF tokens and raw response bodies are never reported.
The only allowed POST is `/api/session/login`. Redirects and system proxies are
disabled; HTTPS retains certificate validation and does not inherit TLS key logging.

Each worker reads the same four routes in order:

- `GET /api/cart` as the customer.
- `GET /api/orders?page=0&size=10` as the customer.
- `GET /api/admin/orders?page=0&size=10` as staff/admin.
- `GET /api/admin/payments?page=0&size=10` as staff/admin.

No catalog seed, cart edit, order checkout, payment/refund operation, logout or
arbitrary route is implemented. Existing isolated data is used as-is. The current
cart service's GET is read-only. Successful login still creates an HTTP session;
this tool does not pretend authentication is side-effect-free.

## Reproduce

Use an isolated seeded commerce runtime and existing demo credentials. Set
`TV3_PERF_CUSTOMER_USERNAME`, `TV3_PERF_CUSTOMER_PASSWORD`,
`TV3_PERF_STAFF_USERNAME`, `TV3_PERF_STAFF_PASSWORD` in the process environment.
Do not put passwords in shell arguments or committed files. Coordinate a quiet
window with browser E2E, builds and other load. The following is a small local
measurement, not the team's proposed 50-user/10-minute acceptance workload:

```powershell
python tests/performance/tv3/read_load.py `
  --base-url http://127.0.0.1:8080 --workers 2 --rounds 20 `
  --warmup-rounds 2 --think-ms 25 `
  --scheduler-note 'Record actual scheduler state or unknown' `
  --db-pool-note 'Record pool configuration and source; telemetry unavailable if not measured' `
  --dataset-note 'Existing isolated demo data, not regenerated by the harness' `
  --window-note 'Record who coordinated the quiet measurement window' `
  --output docs/performance/tv3-read-load.json
```

Defaults yield 160 measured requests (40 per endpoint) and 16 excluded warmups.
Each worker owns two authenticated sessions. Warmups, login and before/after
dataset snapshots are excluded from measured counts and latency. Any warmup or
authentication error aborts the run. Measured request failures are categorized
without server messages; a report is still written and the process exits 1.
There are no retries. Worker count is bounded at 8, rounds at 1,000, warmup rounds
at 20 and each request timeout at 60 seconds.

Per-endpoint and overall results include attempts, successes, categorized errors,
nearest-rank p50/p95, maximum and attempted requests per measured wall second.
Percentiles include failed attempts. Client latency includes HTTP connection,
body reading and JSON parsing; it excludes think time. Throughput uses the shared
measurement window, which includes think time and client scheduling overhead.
Python's urllib connection behavior is part of this workload; no browser or
production connection-reuse claim is made. Cache state is uncontrolled: warmup
does not prove a cache exists, and no cold-cache or hit-rate result is inferred.

## Fixed database evidence

`explain_read.py` uses the installed MariaDB CLI, `--no-defaults`, no shell, fixed
SELECT/EXPLAIN statements, a loopback host and an exact isolated database-name
allowlist. It refuses `furniture_shop`. It accepts only
`furniture_shop_tv3_dev` or `furniture_shop_test_[a-z0-9_]+`.
Credentials are `DB_USERNAME` and `DB_PASSWORD` in the environment; optional
`DB_HOST`/`DB_PORT` default to `127.0.0.1:3306`. The password is supplied to the
child through `MYSQL_PWD`, never an argument, file, SQL statement or report.

```powershell
python tests/performance/tv3/explain_read.py `
  --database furniture_shop_tv3_dev --customer-id 2 `
  --output docs/performance/tv3-explain.json
```

Use the actual seeded customer ID, not an assumed ID. The report records row
counts, server version, existing indexes and fixed representative page/count
plans from `OrderQueryService`, `AdminOrderQueryService` and `PaymentQueryService`,
including filtered order/payment queues. Projections are EXPLAINed, not executed;
personal fields are not returned. Plans describe the existing small dataset and
optimizer estimates. No DDL/DML, `ANALYZE TABLE`, cache flush or index change is
performed, and this is not query-runtime or database-pool-utilization telemetry.

## Harness checks

```powershell
python -m unittest discover -s tests/performance/tv3 -p 'test_*.py'
```

Tests use a temporary loopback HTTP fixture to exercise actual urllib session
login/CSRF, cookie separation, redirect refusal, report redaction and measurement
counts; pure checks cover origin/database guards, nearest-rank percentiles and
empty results. The fixture requires local-network permission if the shell is
sandboxed. It never contacts the application or database.
